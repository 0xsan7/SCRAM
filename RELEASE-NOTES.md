# Release notes and the changelog

**There is no `CHANGELOG.md` in this repository, deliberately.** This
file explains what replaces it, so the absence is a decision you can
check rather than an omission you have to notice.

## What generates the notes

`.goreleaser.yml` has a `changelog:` block that groups conventional
commits into Security / Features / Fixes / Other, excluding `docs:`,
`test:` and `chore:`. GoReleaser renders that into the release body when
it publishes.

Commit subjects in this repository actually follow that convention, so
the grouping has something to work with:

| prefix | count |
|---|---|
| `docs` | 8 |
| `fix` | 7 |
| `feat` | 7 |
| `test` | 6 |
| `ci` | 5 |
| `security` | 1 |
| `release` | 1 |

## Why not a committed CHANGELOG.md

A checked-in changelog is a second source of truth. It is written by
hand or by a bot, and it disagrees with the commit log at some point —
usually silently, and usually the commit log is the one that is right.
Keeping two records of the same history and calling one of them a
document is how a reader ends up trusting the wrong one.

## Why there is a generator anyway

GoReleaser only renders the changelog at publish time. Two consequences,
both verified rather than assumed:

- `goreleaser check` does **not** validate the changelog template. A
  `use:` pointing at a template that does not exist passes `check`.
- `goreleaser release --snapshot` does **not** evaluate it either. The
  same broken configuration produces a clean snapshot build.

So a typo in a group regexp surfaces as *a published release with no
notes*, discovered at the moment the release is being cut — the worst
possible time. The fix is to make the notes reviewable before any tag
exists.

`scripts/gen_changelog.py` does that. It applies the same rules to the
same commit log and prints the result, so the content that will ship can
be read, reviewed and pasted into a release description ahead of time.

```bash
python3 scripts/gen_changelog.py                  # since the last tag
python3 scripts/gen_changelog.py --since v0.1.0
```

The rules are duplicated from `.goreleaser.yml`, which is the real cost
of this approach — two copies of the same grouping. CI closes that gap:

```bash
python3 scripts/gen_changelog.py --check-goreleaser
```

This re-reads `.goreleaser.yml` and fails if a group title, a group
regexp, or an exclude pattern no longer matches. It is run in CI on
every push. Verified by breaking each of the three independently: removing
the `Security` group, changing the `feat` regexp, and removing the
`docs:` exclude each turn it red.

## What is still unverified

GoReleaser v2.5.1 has **no `changelog` subcommand**, so the notes cannot
be generated by GoReleaser into a file before publishing. The
duplicated-rules approach is the workaround, and it has a cost worth
naming: if a future GoReleaser version changes how it interprets these
patterns, `gen_changelog.py` will keep producing output that no longer
matches what the release body will say, and the drift check will not
catch it because it compares against the YAML text rather than
GoReleaser's behaviour.

The first real release is where that gets tested. It has never run.
